# Design decisions

- **Java 21 + Spring Boot 4.1, Maven**: mainstream, well-documented stack for the viva.
- **PostgreSQL 16 + Flyway, `ddl-auto: validate`**: schema changes are versioned migrations, never auto-generated.
- **JVM timezone forced to UTC** (`SentraApplication`): Postgres rejects the `Asia/Calcutta` zone id.
- **Webhook-only alerting**: no email provider, no paid keys.
- **Hysteresis for incidents**: N consecutive failures open an incident, M consecutive successes resolve it, to avoid flapping alerts.
- **SSRF guard**: resolve DNS first, then block private/loopback/link-local addresses.
- **Scheduler claims before probing**: `next_run_at` is advanced in a short transaction using `FOR UPDATE SKIP LOCKED`, then probes are dispatched; this prevents double runs across instances.
- **Bounded probe pool with `AbortPolicy`**: a full queue skips a run instead of blocking the scheduler thread (no `CallerRuns`).
- **Host Postgres port 55432**: avoids clashing with a native Postgres on 5432.
- **Incident state lives on `checks`** (state + consecutive counters, thresholds default 3/2): `EvaluationService` is pure; `IncidentService` applies it under a row lock (`PESSIMISTIC_WRITE`) so overlapping runs of one check can't corrupt counters. A partial unique index allows at most one open incident per check.
- **Alert dedup via insert-first**: the `alert_deliveries` row is inserted (`ON CONFLICT DO NOTHING`) *before* the webhook is sent; the `uq_alert_once` unique index decides who sends. A failed send is recorded as FAILED and not retried (at-most-once). One webhook rule per check (`uq_alert_rule_check_channel`).
- **Alerts are event-driven**: `IncidentService` publishes `IncidentOpened/ClosedEvent`; `AlertListener` handles them `AFTER_COMMIT` on a separate async pool so a slow webhook never holds a probe thread. A reminder sweep (15/30/60 min, then hourly) covers long-open incidents.
- **Tenancy = user -> project -> check**: register creates a default project; user-facing queries (`findByIdForUser`, `findAllForUser`, `findRecentForUser`) embed ownership and return 404 on a cross-tenant hit. Engine code (scheduler, `IncidentService`, `AlertService`) looks checks up by id with no user, deliberately; never call those from a controller.
- **Two filter chains**: `/api/**` needs a JWT (401 otherwise); the public chain permits `/error`, `/actuator/health`, `/ping/**`, `/webhook/**`, `/status/**` and denies the rest. `/error` must be permitted or every API 404/400 is rewritten to 403 (caught by `TenantIsolationTest`).
- **SSRF guard validates, it does not pin**: checked at creation and immediately before each probe/webhook, rejecting if ANY resolved address is internal. A short DNS-rebinding window between that lookup and the connect remains (accepted trade-off; true pinning would need Apache HttpClient 5 with a custom DnsResolver). `sentra.ssrf.allow-private` is for local demos only.
- **Tests need the local Postgres**: `TenantIsolationTest` runs against docker-compose Postgres on 55432 (no Testcontainers) and sets the JVM zone to UTC itself because it bypasses `main`.
- **JWT secret is deny-by-default**: `application.yml` has no default; the placeholder lives only in `application-dev.yml`, and `JwtService` refuses the placeholder unless the `dev` profile is active. Run locally with `-Dspring-boot.run.profiles=dev`.
- **SSRF address rules are an allow-list for IPv6** (only global unicast 2000::/3, minus Teredo and documentation ranges; 6to4 re-checks its embedded IPv4) plus extra IPv4 special-purpose ranges (CGNAT, TEST-NETs, benchmarking, 240/4).
- **Frontend is React + Vite with a dev proxy**: `/api` is forwarded to the backend, so the browser never makes a cross-origin call and the backend has no CORS config. The JWT lives in `localStorage` (acceptable for this scope; an httpOnly cookie would be the hardening step). Pages poll (8s dashboard, 5s detail) instead of using websockets.
- **The "run tape" is the one visual idea**: one bar per run, height = latency, failures full-height red; used on the login screen, dashboard rows and detail page.
- **TLS check = default trust store + warning window**: `TlsProbe` handshakes with the JVM's trust store and HTTPS hostname verification, so an expired, untrusted or mismatched certificate fails the run with a specific message. A valid certificate inside `warnDays` (default 14) also fails, so the existing incident + webhook path warns before expiry (failure/recovery thresholds default to 1/1, interval 1 hour). Like TCP, it connects only to SSRF-vetted addresses within one shared timeout budget (max 3 addresses).
- **Domain expiry over RDAP, not WHOIS**: `DomainProbe` asks `rdap.org`, which redirects to the TLD's registry, and reads the `expiration` event (JSON, no text scraping). It runs daily (at most hourly) and fails inside a warning window (default 30 days), like TLS. Answers that cannot be trusted are `inconclusive` (stored, but neither failure nor success): no RDAP service for the TLD (e.g. `.de`), no published expiry date, registry errors, timeouts. A 404 from the registry itself means "not registered" and does fail. Only the registry is contacted, never the user's domain, so no SSRF guard is needed; the domain is validated by pattern and a pasted URL or `www.` is trimmed. `.com` and `.in` were verified live.
- **CRON checks are evaluated when they are due, not on a timer**: `Probe.nextRunAt` lets a type choose its next run; `CronProbe` returns the ping deadline (+1 s), and a success ping makes the check due immediately. A daily job costs about one run per ping instead of 2,880 a day at the old fixed 30 s; an already-late job is re-evaluated once per period. The check cadence therefore follows the job's own schedule (a 30 s job is checked about every 30 s), and the schedule is free-form in the UI (any value, 10 s minimum).
- **Grace scales with the schedule**: the default allowed delay is 20% of the period, clamped to 10 s – 1 hour (`CronProbe.defaultGrace`, mirrored in the form). A 30 s job may be 10 s late, a 15 min job 3 min, a daily job 1 hour. A fixed 5 min grace was too loose for fast jobs (a 30 s job could miss 10 runs unnoticed) and too tight for long ones. The user can override it.
- **NAT64 is allowed, by its embedded IPv4**: `64:ff9b::/96` addresses (IPv6-only networks with DNS64, such as the dev machine's) pass only if the embedded IPv4 address itself passes the full check, the same rule as 6to4. Previously all NAT64 was rejected, which blocked every public host on such networks.
